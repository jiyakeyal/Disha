# Disha — Team Build and Submission Guide

## 1. Suggested team roles

Adapt these to the number of people; one person can hold more than one role.

- **Conversation designer:** owns dialogue flow, clarifying questions, Hinglish/English tone and answer structure.
- **Research/source steward:** maintains official source links, tests current-page retrieval, checks dates/years and records uncertain facts.
- **UX/UI designer:** owns the chat interface, comparison result, parent summary, mobile/accessibility states and interface copy.
- **Prototype/technical lead:** works with AI Studio Build, checks real server-side model calls, secrets, grounding, error handling and any working voice/upload integration.
- **Test and evidence lead:** runs scenarios, maintains scores and prompt-version log, collects screenshots and summarises iterations.

For a smaller group, divide work by milestones rather than keeping strict roles.

## 2. Seven-day learning plan

### Day 1 — Narrow the brief

- Confirm the name is a working name and define the first target user: for example, a Class 10 student in Gujarat exploring post-Class-10 pathways.
- Agree the exact MVP: real text chat, neutral comparisons, official-source links and parent summary. Keep voice/uploads/profile optional until implementation proves them.
- Choose a small group of career/course paths to smoke-test.

**Output:** one-sentence purpose, audience, in-scope/out-of-scope list and one sample conversation.

### Day 2 — Research and conversation design

- Review the official source entry points in `03_DOMAIN_KNOWLEDGE_AND_SOURCES.md`.
- Select several real official pages relevant to the chosen pathways and note the academic year/effective date.
- Draft and test the system prompt in `02_AGENT_SYSTEM_PROMPT_AND_RULES.md`.
- Design how the agent asks questions without interrogating and how it says “not verified.”

**Output:** source shortlist, initial system instruction and low-fidelity conversation flow.

### Day 3 — Build the working text MVP

- Paste `01_ONE_SHOT_BUILD_PROMPT.md` into Google AI Studio Build and attach companion files.
- Confirm the app has a real server-side Gemini API call and the actual system prompt is applied.
- Test one career exploration question, one comparison and one off-topic request.
- Inspect how errors and API keys are handled.

**Output:** usable text-chat preview and notes on actual blockers.

### Day 4 — Add source verification and result design

- Implement current official-source grounding/retrieval where available.
- Render actual citations and current checking metadata; otherwise present a candid unverified state.
- Add comparison cards/table and one-page parent summary preview/copy.
- Test one past-cycle source versus a current official notice.

**Output:** grounded answer and clear comparison/summary screen.

### Day 5 — Optional features and privacy

- Try voice only if the current Live API is available and the transcript is genuinely generated by the service.
- Try uploads with synthetic/redacted marksheet/checklist examples only, with clear data handling and uncertainty.
- Keep saved profiles disabled for real minors unless real consent, secure storage, access controls, view/edit/delete and review are genuinely implemented.
- If an advanced integration is blocked, show an honest fallback rather than a mock.

**Output:** optional feature decision record and privacy checklist.

### Day 6 — Test and iterate

- Run at least ten tests from `06_TEST_EVALUATE_IMPROVE.md`.
- Capture real app outputs, source links, status and scores.
- Identify one important issue; change one thing; rerun the same test and a regression test.

**Output:** test record and prompt-version log.

### Day 7 — Polish and present

- Fix high-impact clarity, source, accessibility and mobile issues.
- Capture screens that show the user journey and at least one honest failure/unverified state.
- Prepare a short explanation of design rationale, data flow, limits and evidence of iteration.
- Do not call the prototype legally compliant or production-ready without the required validation.

**Output:** working prototype link or local project, prompt pack, visual/evaluation evidence and reflection.

## 3. Small build checklist

- [ ] Welcome screen explains the purpose and choice-preserving approach.
- [ ] Text chat uses real model output and actual runtime system instructions.
- [ ] The agent asks helpful questions and gives neutral, comprehensible options.
- [ ] Current facts use genuine official-source retrieval or are labelled unverified.
- [ ] Citation titles/URLs correspond to actual retrieved source annotations.
- [ ] Comparison result makes trade-offs and unknowns visible.
- [ ] Parent summary is previewed and shared only by user action.
- [ ] API key stays server-side.
- [ ] Uploads and voice are real or visibly disabled.
- [ ] Session and saved-profile behaviour is accurately described.
- [ ] No mentor matching or other unsupported external actions are presented as live.
- [ ] Error, loading, empty and unavailable states are handled.
- [ ] Phone, desktop, keyboard and readable text are checked.
- [ ] At least ten real tests have an honest status and evidence.

## 4. Common blockers and sensible fallbacks

**AI Studio cannot read companion files.** Attach again or paste the system prompt and UX spec directly. Ask the builder to confirm the actual content it consumed. Do not assume attachment makes runtime enforcement automatic.

**The UI works but responses are hard-coded.** Require a real server-side model request and test by asking a new, unpredictable career question. Verify network/server code and failure behaviour without exposing secrets.

**Citations are missing or fabricated.** Inspect the actual API response/grounding annotations. Render only returned citations. If none are available, label the answer unverified and link the official portal; do not make up a source card.

**The model returns stale dates.** Require current official retrieval and academic-year matching. If that is unavailable, make the response candidly unverified. Do not “fix” it by hard-coding a date that will expire.

**Voice API is unavailable or confusing.** Disable voice for the demo and retain text. Never animate fake transcript text or present browser dictation as Gemini Live without identifying the actual path.

**Upload reading is unreliable.** Use redacted test images, show uncertainty and ask for confirmation. If safe processing/deletion cannot be demonstrated, disable uploads.

**Saved profile consent/storage is too much for seven days.** Keep the product session-only for real people, show saved profiles as not enabled, and use fictional data for any design demonstration. A checkbox alone is not a valid substitute for a verifiable parent-consent flow.

**Costs or rate limits block testing.** Confirm project billing/quotas and current feature pricing. Use fewer controlled tests and an honest fallback. Do not claim a service is free because a sign-in is free.

**The scope feels too broad.** Keep the default journey to one target case: student after Class 10 comparing two or three pathways in Gujarat. Retain other features as clearly labelled extensions.

## 5. Evidence to capture from real tests

Take screenshots or short recordings of:

1. Onboarding and the clean chat interface.
2. A real user question and actual response, including a useful clarifying question.
3. A comparison of options, including trade-offs.
4. A current-fact question with real official citations **or** the explicit unverified fallback.
5. The parent-summary preview before copying/downloading.
6. At least one source failure/blocked feature handled honestly.
7. Mobile and keyboard/accessibility checks.
8. A test sheet showing actual scores/statuses and one baseline → change → retest iteration.

Never include API keys, tokens, full student documents, identifying marksheets or real minors' personal data in screenshots. Use synthetic details for demonstration. A screenshot proves only what it shows; it does not prove the unseen backend is secure or all cases work.

## 6. One-page blueprint checklist

Use this as the final group review sheet.

- [ ] **Purpose:** One narrow, useful user problem is clear.
- [ ] **Audience:** User and co-user are named; minor safeguards are addressed.
- [ ] **Agent identity:** Disha's role, tone and limits are clear.
- [ ] **User flow:** first question → clarification → comparison → sourced next step → parent summary.
- [ ] **System prompt:** installed as actual system-level runtime instructions, not just visible text.
- [ ] **Knowledge:** official sources are relevant, current-year aware and labelled with limits.
- [ ] **Context/memory:** session context differs from persistent profile; no false memory claims.
- [ ] **Privacy:** data minimisation, upload warnings, parental-consent gate, access and deletion plan.
- [ ] **Architecture:** actual model/tool path, server-side secrets, honest failures.
- [ ] **Boundary cases:** out-of-scope, bad assumptions, prompt injection, uncertainty and sensitive upload.
- [ ] **Sample conversations:** include common success, uncertainty and off-topic examples.
- [ ] **Screenshots/UI:** clean, accessible, responsive and free of exposed secrets.
- [ ] **Iteration evidence:** baseline, one change, retest, scores and prompt log.
- [ ] **Limitations:** blocked integrations and untested behaviour are stated honestly.

## 7. Suggested presentation structure

1. The student problem and why facts/trust matter.
2. Target users and the one chosen journey.
3. Conversation principles: ask, compare, verify, preserve student agency.
4. Interface screens and source presentation.
5. Actual system instruction and how it is applied at runtime.
6. Data flow, current-source verification and privacy boundary.
7. Testing evidence and one iteration.
8. What works, what does not yet work, and next steps for responsible expansion.

A good Communication Design outcome is not the number of features. It is a clearly scoped, usable conversation whose claims, controls and limitations match what the system really does.
